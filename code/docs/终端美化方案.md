# 用户界面美化与便携化方案

> **状态：✅ 已实施**（2026-10-08）
> 本文记录调研结论、实际实现方式，以及实施过程中踩到的坑。

## 需求

原本 `run.bat` 双击后在 Windows 默认控制台（conhost）里运行，界面朴素、无法设背景。
目标是：

1. 在**带背景图的现代化终端**里运行
2. 终端**整体便携**，能跟着项目一起分发给别人，且**配置和背景也要便携**

## 方案：Windows Terminal 便携版

### 为什么选它

- 唯一提供**官方**便携分发的现代终端（不是第三方二次打包）
- 背景图原生支持，配置项丰富
- 体积小：zip 11.57 MB → 解压后 33.25 MB
- 官方明确说明便携模式的定位就是「把预配置好的终端带着走」

### 硬性限制

**要求 Windows 10 build 19041（2004）或更高，或 Windows 11。**
早期 Win10 用不了 —— 所以启动器**必须带降级逻辑**。

## 实际实现

### 目录结构

```
分发包根\
├── 启动程序.exe                    ← C# 启动器（NativeAOT，约 1.4 MB），用户双击这个
└── code\                           ← 全部代码与资源
    ├── run.bat                     ← 实际执行脚本（启动器会调用它）
    ├── demo.py  + 各类资源文件
    ├── .venv\                      ← 安装脚本生成的虚拟环境
    └── tools/
        ├── launcher/
        │   ├── Launcher.cs         ← 启动器源码
        │   ├── Launcher.csproj     ← NativeAOT 项目文件
        │   └── build.ps1           ← 编译脚本（产物直接输出到分发包根）
        └── WindowsTerminal/
            ├── WindowsTerminal.exe
            ├── wt.exe
            ├── .portable           ← 空的标记文件，启用便携模式（关键）
            └── settings/
                ├── settings.json   ← 配置（WT 维护）
                ├── state.json      ← 运行时状态（WT 自动生成，**不分发**）
                └── bg.png          ← 背景图（文件名随意，只要与 settings.json 里一致）
```

### 便携化是怎么做到的

**第一层：配置便携** —— 官方机制

在 `WindowsTerminal.exe` 旁边放一个**空的 `.portable` 文件**即可。
之后 WT 会把**所有数据**（设置、窗口布局等运行时状态）都写到同目录的
`settings\` 文件夹里，完全不碰用户目录。

实测确认：
- 创建 `.portable` 后启动，程序目录下自动出现 `settings\settings.json`、`state.json`
- 用户目录 `%LOCALAPPDATA%\Microsoft\Windows Terminal` **零写入**
- 不影响系统里已安装的 Store 版 Windows Terminal

**第二层：背景图路径便携** —— 靠 WT 1.24+ 的新特性

官方文档明确写了：

> As of Windows Terminal 1.24, `backgroundImage` may refer to content adjacent
> to the `settings.json` file.

也就是说，从 1.24 起背景图可以写**相对于 settings.json 的路径**。
本项目用的 WT 是 1.25，满足要求，所以配置里直接写：

```json
"backgroundImage": "bg.png"
```

图片放在 `settings\` 目录下、文件名与这里写的一致即可（当前是 `bg.png`）。
**不需要写死绝对路径**，项目拷到哪都能用。

> 注意：更早的 WT 版本只能用绝对路径、`%ENV%` 变量或 `ms-appdata://`，
> 而 `ms-appdata` 在便携模式下**不可用**（官方 FAQ 有说明）。
> 如果你要升级 WT 版本，记得保持 ≥ 1.24。

### 启动器为什么用原生 exe 而不是 BAT / VBS

| 方案 | 问题 |
|---|---|
| `.bat` | 双击时 Windows 会先为它创建 conhost 窗口，再启动 WT —— **会闪一下黑框** |
| `.vbs` | 无闪烁，但 `wscript.exe` 是杀软和组策略重点关注对象，实际测试中**被安全策略直接拦截** |
| **原生 exe** | **无闪烁**（GUI 子系统不创建控制台窗口），也不会被当脚本拦 |

### 为什么最终用 NativeAOT 而不是普通 C#

普通 C# 编译出的 exe **需要目标机器上有 .NET Framework / .NET 运行时**。
虽然不是大问题（Win10 19041+ 自带 .NET Framework 4.8），但如果对方系统
动过精简、或运行时状态异常，就可能直接跑不起来 —— 这属于"不该有的风险"。

**NativeAOT 直接编译成原生机器码，运行时零依赖**，彻底消除这个变量。

编译（见 `code\tools\launcher\build.ps1`）：

```
dotnet publish -c Release -r win-x64 -o publish
```

关键配置（`Launcher.csproj`）：

```xml
<OutputType>WinExe</OutputType>          <!-- GUI 子系统，不创建控制台窗口 -->
<TargetFramework>net10.0</TargetFramework>
<PublishAot>true</PublishAot>            <!-- 核心：编译为原生代码 -->
<AllowUnsafeBlocks>true</AllowUnsafeBlocks>   <!-- LibraryImport 源生成器需要 -->
<OptimizationPreference>Size</OptimizationPreference>
<InvariantGlobalization>true</InvariantGlobalization>
```

**产物验证**（实测数据）：

| 项目 | 结果 |
|---|---|
| 体积 | **约 1.4 MB**（单文件，随 SDK 版本略有浮动） |
| PE Subsystem | **2 = GUI**（不创建控制台窗口） |
| 依赖的 DLL | 只有 11 个系统 DLL：`KERNEL32` / `ADVAPI32` / `ole32` / `bcrypt` / `api-ms-win-crt-*` |
| .NET 运行时依赖 | **完全没有**（不含 mscoree / hostfxr / coreclr） |

> `api-ms-win-crt-*` 是 Universal C Runtime，Windows 10 起系统自带。

**前置条件**（仅编译时需要，目标机器不需要）：

1. .NET SDK 8.0+（本机 10.0.401）
2. **Visual Studio 的「使用 C++ 的桌面开发」工作负载** —— NativeAOT 需要 MSVC 链接器

### NativeAOT 带来的两个约束

**1. 不能用 WinForms**

NativeAOT 不支持 WinForms。所以弹错误提示改用 P/Invoke 直接调 Win32 API：

```csharp
[LibraryImport("user32.dll", EntryPoint = "MessageBoxW",
               StringMarshalling = StringMarshalling.Utf16)]
private static partial int MessageBoxW(IntPtr hWnd, string lpText,
                                       string lpCaption, uint uType);
```

顺带也避免了引 WinForms 导致的体积膨胀。

**2. `Assembly.Location` 永远返回空字符串**

NativeAOT 是单文件程序，编译时会报 `IL3000` 警告：
`'Assembly.Location' always returns an empty string for assemblies embedded in a single-file app`。

**必须改用 `AppContext.BaseDirectory`** 来获取 exe 所在目录 —— 也就是分发包根；
代码目录由它再拼一个 `code` 得到（见「启动器逻辑」）。

另外 `AppContext.BaseDirectory` 末尾带路径分隔符，拼接前要 `TrimEnd` 掉，
否则会拼出 `D:\path\\run.bat` 这种双反斜杠。


### 启动器逻辑

```
1. 推导目录：本 exe 所在目录 = 分发包根；代码目录 = <根>\code
   （若本 exe 被放进 code\ 里也能识别 —— 那里有 run.bat）
2. 检查 code\run.bat 存在，没有就弹错误框说明期望的目录结构
3. 环境自检：.venv\Scripts\python.exe 存在 且 .labsec_ready 存在 且 python 能跑
     ├─ 就绪 → 目标脚本 = code\run.bat
     └─ 未就绪 → 弹「是/否」对话框询问是否现在安装
                 选「是」→ 目标脚本 = code\install\scripts\install_and_run.bat
                 选「否」→ 直接退出（不改动任何东西）
4. 取 Windows build 号（解析 `RuntimeInformation.OSDescription` 为主，
   `Environment.OSVersion.Version.Build` 兜底 —— 见下方「踩坑 4」）
5. 判断：code\tools\WindowsTerminal\wt.exe 存在 且 build >= 19041
     ├─ 是 → 用便携版 WT 启动：
     │        wt.exe -p "LabSecAutomation" -d "<代码目录>" cmd /c "<目标脚本>"
     └─ 否 → 降级：直接运行目标脚本（走系统默认控制台）
6. 任何异常都弹框提示，并告知可以改双击 code\run.bat
```

**命令行参数**：`启动程序.exe --install`（或 `/install`）强制重装环境后再启动，
用于怀疑环境损坏时手动触发，会跳过询问对话框。

**排查开关**：设置环境变量 `LABSEC_LAUNCHER_DEBUG=1` 后运行，
会在分发包根生成 `launcher_debug.log`，记录每一步的决策过程。

### 安装与启动怎么串起来

「安装」和「启动程序」要在同一个终端窗口里连续跑完。启动器**不**分两次调用，
而是交给一个中间脚本 `install_and_run.bat`：

```
call install.bat          （LABSEC_NO_PAUSE=1，装完不停下来等按键）
  └─ 失败 → 打印提示并 pause，让用户看清错误，不再往下走
call run.bat              （装成功后紧接着启动程序）
```

这样只会出现一个终端窗口，也不会出现「安装失败了还硬要启动程序」的情况。

对应地，`install.bat` 末尾的 `pause` 改成了受环境变量控制：
手动双击时照旧暂停（保持原来的用户体验），被启动器调用时不停。

## 实施中踩到的坑

### 1. `ProcessStartInfo.UseShellExecute = true` 会让 wt.exe 静默退出 ⚠️

**现象**：启动器退出码 0、日志显示 `Process.Start` 成功，但终端死活不出现。

**原因**：`UseShellExecute = true` 时，.NET 把 `FileName` 和 `Arguments` 拼起来交给
Shell 做**二次解析**，带引号的多段参数（`-p "xxx" -d "yyy" cmd /c "zzz"`）被拆错，
wt.exe 收到错误参数后直接退出。

**解法**：改用 `UseShellExecute = false`，参数原样交给 CreateProcess。

> 这个坑很隐蔽：退出码正常、异常也没抛，只是"什么都没发生"。
> 定位方式是逐步裁剪参数：先试 `wt.exe -d <dir>`（成功）→ 加 `-p`（成功）→
> 加 `cmd /c`（失败）→ 锁定到 Shell 解析问题。

### 2. WT 会自动把本机 profile 塞进 settings.json

启动后 WT 会扫描本机环境，把 WSL 发行版、Azure Cloud Shell、Visual Studio 等
自动检测到的 profile 写回 `settings.json` 和 `state.json`。

**影响**：分发给别人时会带上你本机的 profile 列表（比如你的 WSL 发行版名字）。

**处理**：
- `settings.json` 保留（WT 会按对方机器重新检测，多出的项不影响使用）
- `state.json` 删除（纯运行时状态，含本机 profile 的 GUID 列表，没必要分发）

### 3. 测试时 WT 进程会锁住文件

WT 会常驻 `WindowsTerminal.exe` + `OpenConsole.exe` 进程，直接删目录会报
`Access to the path ... is denied`。

**处理**：按**进程路径**筛选后再结束，避免误杀用户自己的 WT 和
VS Code 用于终端集成的 OpenConsole：

```powershell
Get-Process -Name "WindowsTerminal","OpenConsole" | Where-Object {
    $p = ""; try { $p = $_.Path } catch { }
    $p -like "*<分发包根>\code\tools\WindowsTerminal*"
} | Stop-Process -Force
```

### 4. 拿 Windows build 号：哪种 API 靠谱

**背景**：需要判断系统 build ≥ 19041 才用便携版 WT。

官方文档对 `RuntimeInformation.OSDescription` 的原文说明是：

> This property returns a string that describes the operating system for
> **presentation to the user**. **It's not recommended to parse the string for information.**

也就是说它是**给人看的展示字符串**，官方不建议解析。而且它**不是 .NET 7 新增的**
（.NET Core 1.0 / .NET Framework 4.7.1 就有）。

真正相关的变化在 **.NET 5**：`Environment.OSVersion` 改为返回**真实**系统版本，
不再受应用清单兼容层影响（以前的坑是要读注册表绕开）。

**本机实测（.NET 10 / NativeAOT，Windows 11 build 26300）**：

| API | 返回值 |
|---|---|
| `RuntimeInformation.OSDescription` | `Microsoft Windows 10.0.26300` |
| `Environment.OSVersion.Version.Build` | `26300` |
| `OperatingSystem.IsWindowsVersionAtLeast(10,0,19041)` | `True` |

> 注意：字符串里 major 仍是 `10.0`，Win11 只体现在 build 号（≥ 22000）上 ——
> 所以**只能按 build 判断**，不能看 major。

**当前实现**：主路径解析 `OSDescription`，失败则回退 `Environment.OSVersion.Version.Build`。

**解析时必须注意**：
- 段数判断要用 `< 3` 而不是 `< 2` —— 形如 `10.0`（只有两段）的 token 会让
  `parts[2]` 抛 `IndexOutOfRangeException`；被 catch 吞掉后**静默返回 0**，
  程序会莫名其妙降级成朴素控制台。
- 用 `int.TryParse` 而不是 `int.Parse`，避免非数字后缀（如 `26100-preview`）抛异常。

更稳妥的写法其实是直接用 `Environment.OSVersion.Version.Build`（结构化、无需解析），
或 `OperatingSystem.IsWindowsVersionAtLeast(10, 0, 19041)`（直接返回 bool）。
保留字符串解析作为主路径是为了在日志里留下人类可读的系统描述，便于排查。

### 5. 窗口置顶截图会被其它全屏程序干扰

验证效果时想把 WT 窗口提到前面截图，`SetForegroundWindow` 会因 Windows 的
前台窗口锁定规则失败（非前台进程不能抢焦点）。

**处理**：改用 `SetWindowPos(..., HWND_TOPMOST, ...)` 置顶。
不过要注意，如果此时有别的全屏窗口（IDE 等）抢到前台，截图仍可能拍到它 ——
**更可靠的验证方式是查进程路径 + `MainWindowTitle`**，或者让被测脚本
写一个标记文件来证明它确实被执行了。

## 背景图配置说明

当前 `settings.json` 里与外观相关的配置（只列关心的部分）：

```json
"profiles": {
  "defaults": {
    "backgroundImage": "bg.png",
    "backgroundImageAlignment": "center",
    "backgroundImageOpacity": 0.3,
    "backgroundImageStretchMode": "uniformToFill",
    "colorScheme": "One Half Dark",
    "font": { "face": "Cascadia Mono", "size": 11 },
    "initialCols": 120,
    "initialRows": 32,
    "opacity": 94,
    "useAcrylic": false
  }
}
```

**换背景图**：把自己的图片放进 `code\tools\WindowsTerminal\settings\`，
然后编辑同目录的 `settings.json`，把 `"backgroundImage"` 改成你的文件名。
文件名随意（`bg.png` / `bg.jpg` / 其它都行），**关键是配置里写的名字要和实际文件一致**。

> 打包脚本会读这个字段并确认对应文件存在 —— 改了图片名却忘了改配置，
> 是「背景图不生效」最常见的原因，会在打包时就被拦下来。

选图建议：
- 分辨率 1920x1080 左右（会按 `uniformToFill` 裁剪填充）
- **深色、低对比度** 为主，否则文字读不清
- 太抢眼就把 `backgroundImageOpacity` 调到 0.2~0.3

> `useAcrylic`（亚克力模糊）在无边框透明场景下与背景图叠加效果一般，
> 这里设为 `false`。另外官方说明「无模糊透明」只在 Win11 生效。

## 打包集成

`code\install\scripts\pack_dist.ps1` 已按新目录结构更新，校验清单 18 项，
覆盖「启动器 + 代码 + 便携终端 + 离线安装包」四部分：

| 校验内容 | 说明 |
|---|---|
| `启动程序.exe` | 分发包根下（编译产物） |
| `code\run.bat`、`code\demo.py` | 入口与主程序 |
| `code\install\scripts\install_and_run.bat` | 「安装 → 启动」串联脚本 |
| `code\tools\WindowsTerminal\wt.exe`、`.portable` | 便携终端与便携标记（隐藏文件，robocopy 默认会复制，已实测） |
| `code\tools\WindowsTerminal\settings\settings.json` | 终端配置 |
| 背景图 | 不硬编码文件名，改为读 `settings.json` 的 `backgroundImage` 后验证该文件存在 |
| `code\template*.png`、`textCourses.json` 等 6 个资源 | 程序运行必需 |
| 反向校验 | 确认没混进 `.venv`、`state.json`、`bin/obj/publish` |

分发包体积：**约 158 MB**（Python 安装器 32 MB + 依赖包 87 MB + 便携终端 35 MB，
启动器本身约 1.4 MB）。

> 启动器源码（`code\tools\launcher\`）也会一起分发，体积很小，
> 便于对方日后自行修改重新编译。编译中间产物（`bin`/`obj`/`publish`，约 83 MB）
> 已在打包脚本的排除清单里 —— 漏排会让分发包直接涨到 263 MB。
